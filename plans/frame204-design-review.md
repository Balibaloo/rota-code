1. **The fallback conflict row holds the merge on a page ruling after intent.** `plans/frame204-design.md:128-130` and `:203`. Severity high. CONFIRMED by reading. A `conflict` row with no edge goes on the page as a numbered line and holds `mergeable` until it closes. Only `principal.land` or `decisions.author` with `resolves_ledger` closes a ledger row (`principal.py:1814`, `api.py:8073`, the map of `ledger`, 2026-10-11). No owner seat is woken by a ledger row, so the principal's keypress is the only discharge. That is a wait on a page, against DECISIONS 2026-09-12 point 2, "After that, nothing waits on a page". Section 5 says the merge never waits on a page except for Q1, which is false for this path under `merge_gate = auto`. Fix: under `auto`, a fallback conflict row does not hold the merge and parks with the others. Under `review` it holds as a line.
2. **A batch held by a quarantined message never moves again, and nothing the design adds releases it.** `plans/frame204-design.md:150` and `:161`. Severity high. CONFIRMED by grep. No code moves a message out of `quarantined`. So the batch waits for a person to edit the database. Meanwhile the `quarantined` predicate (`predicates.py:1590`) wakes the Liaison, so the principal sees an abandoned item. The same gap holds for a question that the Tester's triage creates `unresolved`, which nobody owes a reply (`schema.sql:692-693`). Fix: name the discharge, for example a decision that refs the quarantined message releases it. Drop `unresolved` from the predicate or limit it to messages the ladder still carries.
