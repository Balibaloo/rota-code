## 5. The options

**(a) A plugin that makes `invoke` default to `catch_exceptions=False`.** Mechanism: the harness puts a plugin on the pytest line, and the plugin wraps `click.testing.CliRunner.invoke` once `click.testing` is imported. Files: `harness.py` (argv, plugin file), `execute.py` (an `env` parameter, or the file written into the worktree), a new plugin module. Tests today: `tests/rota/test_execute.py:27` checks `argv[1:3]` only; `test_developer.py:119-692` and `test_delivery.py:265-318` run the real harness. Cost: one implementer pass, 0 re-records (reasoned: L1 cases give `test_runs.output` as fixture text). Risk: high when the project is click. The patched class is the code under test (`src/click/testing.py`). On all of click's own tests at 3eebc90 the global default turns 3 failed into 23 failed: 20 project tests go red, among them `test_testing.py::test_catch_exceptions` and the `test_stream_lifecycle` exception tests (observed: `rota_nocatch.py`, two runs). Scoped to the batch's own tests (`own` is already known at `harness.py:108`), the project is safe. But a Tester test that asserts a caught exception goes red: up to 11 of the 57 night bodies assert `result.exception`, `exc_info` or a non-zero exit (observed: the count; an upper bound, because a `SystemExit` exit still works).

**(b) The harness re-renders a red row from the `Result`.** Impossible from outside. The `Result` lives in the pytest child, and the harness gets text (`execute.py:33-40`). The output holds `result.output`, which is empty, and nothing of the exception (observed: tr532). Any version that works puts code inside the test process, which is (d).

**(c) A Tester brief line or a door on `tests.encode`.** A brief line in `tester/base.md` moves 3 prompt hashes and all 13 recorded Tester cases: `18597259…` (7 cases, `tests_missing`), `e75e02e5…` (2, `answer`), `fd35103e…` (4, `challenge`). All three modes carry `tests.encode` (observed: `count_tester.py` on `tests/rota/cassettes.db`). A line in `tests_missing.md` alone moves 7 and misses the two modes that rewrite tests. A door moves 0 prompt hashes, and no recorded Tester case encodes an `invoke` (observed: grep of the cases). Cost: one pass plus 13 re-records for the line, one pass for the door. Risk: the door fails the certainty test of `DECISIONS.md:943`, and the line is stochastic. Neither covers a project test, and neither changes the `raised at` that pointed at the test.

**(d) Better: a reporting plugin that keeps the test's semantics.** Mechanism: the harness runs every test with a plugin that wraps `invoke`, keeps each `Result` whose `exc_info` is not `SystemExit`, and appends that traceback to a failed test's report. A passing test and its assertions do not change. Click's own suite with the probe plugin: 3 failed, 1910 passed, the same as without it (observed: two runs). Files: as (a), plus `api.py:7076-7078` for a `raised at` wording when a caught exception follows an assertion. Design points: relative paths and the last frames only, so the section and the assertion fit the 2000-character tail; the plugin file stays out of the diff like the materialised tests (`api.py:7041`); the plugin does nothing when `click.testing` is never imported. Cost: one implementer pass, about 300k cold, 0 re-records (reasoned: as (a)). Risk: low. A batch that changes `CliRunner.invoke` itself still meets a wrapper, but the wrapper passes every argument and the return value through.

## 6. Recommendation

Option (d), the reporting plugin. It puts the caught exception and the `NameError` line into the red row while every test keeps its pass or fail, so click's own suite does not move (3 failed with and without it) and no Tester case re-records. It also turns the false `raised at ... the test's own assertion` of night 138 into a pointer at `src/click/decorators.py:508`, which neither (a) scoped nor (c) gives for every test.

The ends-when's ratio, restated: Developer attempts on a batch that end red on a hidden exception, from 8 of 8 on night 138's b_3 to at most 1 in 5 on the walk, with the residue rule of frame 193. Note: the record keeps 4 of those 8 attempts, 4, 6, 7 and 8 (observed: `test_runs` for b_3). The likely cause is that a run deletes the older rows at its commit (reasoned: `harness.py:113`). The 8 come from the read's count of the attempts.
